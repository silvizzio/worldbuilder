Every digital twin in WORLD BUILDER is assembled from six objects. Learning them as a structure rather than a glossary is worth the ten minutes, because the nesting answers two questions that come up constantly: which panel do I open to change this, and what breaks if I change it.

## Why an object model matters here

3D projects tend to fail in a predictable way. They start simple, accumulate assets and annotations, and reach a point where nobody is certain where a given piece of configuration lives or what depends on it. Changing a model breaks an annotation nobody remembers creating. Two people configure the same thing in different places.

WORLD BUILDER avoids this by making the containment explicit. Each object has exactly one home, one panel that configures it, and a defined relationship to the objects above and below it. That is what makes a project handed between team members legible rather than archaeological.

## Object model

| Concept | What it is | Where you configure it |
| --- | --- | --- |
| Project | The container for one digital twin experience. Holds identity, type, cover image, scene settings, assets, markers, UI, and publishing state. | [Project Settings](/en/docs/editor/editor-panels/scene-panel/project-settings) |
| Scene | The 3D environment opened in the editor and the preview. Defines the viewing context for everything placed inside it. | [Feature Panels](/en/docs/editor/editor-panels/) |
| Model Asset | A 3D resource representing an object, space, map area, or supporting element. | [Asset Management](/en/docs/editor/editor-panels/model-panel/asset-management) |
| Marker | A spatial annotation attached to a position or model. Carries text, image, video, or data, and can trigger an interaction. | [Add Marker](/en/docs/editor/editor-panels/marker-panel/add-marker) |
| UI Layer | A 2D interface layer drawn on top of the 3D scene, containing pages and components. | [Page & Component Management](/en/docs/editor/editor-panels/ui-panel/page-and-component-management) |
| Publish State | The delivery status of the project: saved, previewed, shared, or public. | [Publish Project](/en/docs/editor/project-actions) |

## How they nest

The project is the operating container. Inside it, model assets form the visible 3D content, scene settings govern how that content is viewed, markers add spatial information on top, and UI layers sit above everything as the 2D control surface.

That order is also a dependency chain, which is the practically important part.

| If you change | What may need revisiting |
| --- | --- |
| Project type | Default camera controller, and how model placement reads |
| A model's position or scale | Any marker attached to it, and any fly-to viewpoint framing it |
| A model's existence | Marker attachments, and UI interactions targeting that model |
| A UI page's name or existence | Marker interactions that show or hide that page |

Nothing here is fragile, but the chain runs one way. Building in the same direction, scene settings then assets then markers then UI, means each layer is placed against something already settled. Building against the chain means revisiting work you have already done.

## Asset levels

Asset level describes the scale of the 3D content, and it determines the project type you choose at creation.

| Asset level | What it covers | Typical use | What it changes about authoring |
| --- | --- | --- | --- |
| Map-level | Large-scale reconstructed geography, city blocks, campuses, outdoor scenes | Spatial display, urban context, infrastructure review | Wide initial views, markers used for location-bound data |
| Space-level | Interiors, rooms, buildings, facility environments | Walkthroughs, indoor scenarios, space inspection | First-person navigation, UI used to guide a route |
| Object-level | Individual objects, equipment, products, vehicles, components | Product display, asset inspection, equipment explanation | Tight framing, visibility toggles to reveal internals |

The level is not just a label. It shapes which controls matter: a map project lives or dies on its initial camera view, while an object project depends far more on lighting and visibility control.

## Who does what

The object model maps onto team roles almost exactly, which is the main reason it is worth internalising.

| Role | Owns | Works in | Hands off |
| --- | --- | --- | --- |
| Project owner | Project identity and lifecycle | Project Center, Project Settings | A created, typed project ready for assets |
| 3D content operator | Asset preparation and placement | Model Panel, Debug Tools | A stable scene with assets correctly positioned |
| Solution engineer | Markers, UI, and interactions | Marker Panel, UI Panel | A configured, interactive experience |
| Reviewer | The saved or published output | Preview and share links | Feedback against a specific saved version |

The handoff column is the useful one. Each role finishes at a point the next can build on, so the sequence works as a pipeline rather than as a scramble.

## Why it matters

A clear object model reduces confusion as projects grow. Teams can tell where each type of configuration belongs, keep assets organised, and make later editing, review, and maintenance predictable rather than exploratory.

It also makes reuse practical. A project whose structure is understood can be duplicated and adapted for a new customer, a new site, or an updated capture. A project nobody can navigate gets rebuilt from scratch, which is where the cost of a 3D programme usually accumulates.

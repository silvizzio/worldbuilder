The **online editor** is where a project stops being a 3D file and becomes something a customer can use.
Positioning models, labelling them, building the interface, and publishing all happen in one browser tab.

That is worth pausing on, because most teams do this with three separate tools.
A 3D application to position the models, a document to hold the annotations,
and a developer to build the viewer a customer eventually sees.
Every change means a trip through all three, which is why 3D deliverables
tend to be finished once and never touched again.

In the editor, a change takes minutes and the result is a link you can send immediately.
There is no local install, no game engine, and no build step.

## Why the editor is panel-based

A digital twin scene involves four concerns, and they belong to different people at different moments.
Combine them into one interface and you get specialist software.

Separating them keeps each concern independent:

- A **3D content operator** places assets without touching interaction logic
- A **solution engineer** builds the UI layer without needing to understand asset alignment
- Both work in the same project without obstructing each other

| Panel | Owns | Typically operated by | Documentation |
| --- | --- | --- | --- |
| Scene Panel | Project identity, camera behaviour, lighting, post-processing | Project owner, 3D operator | [Scene Panel](/en/docs/editor/editor-panels/scene-panel/project-settings) |
| Model Panel | Bringing 3D models in, positioning them, checking they sit right | 3D content operator | [Model Panel](/en/docs/editor/editor-panels/model-panel/asset-management) |
| Marker Panel | Labels pinned to the scene, and what happens when you click them | Solution engineer | [Marker Panel](/en/docs/editor/editor-panels/marker-panel/add-marker) |
| UI Panel | The flat interface on top: pages, buttons, text, and what they do | Solution engineer | [UI Panel](/en/docs/editor/editor-panels/ui-panel/canvas-settings) |

Alongside the panels, project actions handle save, preview, publish, and undo. See [Publish Project](/en/docs/editor/project-actions).

## Working order

The panels are independent, but scenes come together in a fixed order.

1. Configure the scene
2. Load and place assets
3. Attach markers
4. Build the UI above them

Each layer references positions the previous one established:

- Move a model after markers are attached, and every marker on it needs revisiting
- Build UI interactions before their target pages and models exist, and you build them twice

[End-to-End Workflow](/en/docs/end-to-end-workflow) sets out the full ten-step path and where teams commonly lose time.

## What the editor replaces

| Conventional approach | In the editor |
| --- | --- |
| A 3D application for positioning models | Model Panel, with drag handles and typed values |
| A document or spreadsheet holding annotations | Markers attached to the positions they describe |
| A developer building a front end around the asset | UI Panel, with pages, components, and interactions |
| A deployment step to make changes visible | Save, preview, share, inside the same workspace |

The cost comes from repeating all three every time the scene changes.

## Why it matters commercially

- **During a review**: feedback can be addressed and reshared in minutes rather than deferred to the next iteration, so reviews converge instead of accumulating
- **Across a team**: scene configuration, annotation, and interface design become tasks for a solution engineer rather than a 3D specialist

The second point removes the reconstruction team as the bottleneck for every customer variant and every presentation.

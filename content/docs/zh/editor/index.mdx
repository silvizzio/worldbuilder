在线编辑器是项目从「一个三维文件」转变为「客户可用的成果」的地方。它把三维视口、四个功能面板、模型资产、标记、界面图层与发布控制集中在同一个网页端工作区中。

这里的任何工作都不需要本地安装、游戏引擎或构建步骤。这正是关键所在：配置场景的人，可以就是理解这个场景需要传达什么的人。

## 编辑器为何采用面板化结构

一个数字孪生场景包含四类不同的关注点，它们在不同阶段分属不同的人。把它们混在同一个界面里，正是三维工具沦为专业软件的原因。

面板化的划分让每类关注点彼此独立、各自可达。三维内容运营可以摆放资产而不必触碰交互逻辑；解决方案工程师可以搭建界面层而无需理解资产对齐。两者在同一个项目中工作，互不干扰。

| 面板 | 负责范围 | 通常由谁操作 | 文档 |
| --- | --- | --- | --- |
| 场景面板 | 项目标识、相机行为、灯光、后处理 | 项目负责人、三维内容运营 | [场景面板](/zh/docs/editor/editor-panels/scene-panel/project-settings) |
| 模型面板 | 资产上传、摆放与调试 | 三维内容运营 | [模型面板](/zh/docs/editor/editor-panels/model-panel/asset-management) |
| 标记面板 | 空间标注及其交互 | 解决方案工程师 | [标记面板](/zh/docs/editor/editor-panels/marker-panel/add-marker) |
| 界面面板 | 二维页面、组件及组件交互 | 解决方案工程师 | [界面面板](/zh/docs/editor/editor-panels/ui-panel/canvas-settings) |

除面板之外，项目操作负责保存、预览、发布与撤销，详见[发布项目](/zh/docs/editor/project-actions)。

## 工作顺序

各面板彼此独立，但场景的搭建遵循可预期的顺序：先配置场景，再加载并摆放资产，然后添加标记，最后在其上构建界面。

每一层都会引用上一层已确定的位置。在附加标记之后移动模型，其上的每个标记都需要重新调整；在目标页面与模型尚未存在时就配置界面交互，则等于要做两遍。完整的十步路径，以及团队因逆序操作而损失时间的常见情形，请参见[端到端工作流](/zh/docs/end-to-end-workflow)。

## 编辑器取代了什么

对多数团队而言，把三维资产变成可展示成果的现有流程，通常涉及三套工具和至少一次交接。

| 传统做法 | 在编辑器中 |
| --- | --- |
| 用三维软件完成摆放与布局 | 模型面板，支持操作手柄与参数控制 |
| 用文档或表格保存注释 | 标记直接附着在其所描述的位置上 |
| 由开发人员围绕资产搭建前端 | 界面面板，提供页面、组件与交互 |
| 需要部署步骤才能让改动生效 | 保存、预览、分享，都在同一工作区内完成 |

传统做法的代价不在于其中任何单独一步，而在于往返：场景的每一次改动都意味着重新导出、重新标注、重新部署。这正是三维交付物往往「做完一次就再也不更新」的原因。

## 商业层面的意义

把创作与发布收拢到同一处，改变了评审周期中「什么是可行的」。干系人的反馈可以在几分钟内被处理并重新分享，而不必排进下一轮迭代，这让评审得以收敛，而不是不断累积。

它也改变了「谁能做这件事」。场景配置、标注与界面设计成为解决方案工程师的工作，而非三维专家的工作，于是重建团队不再是每个客户变体、每场演示的瓶颈。
